## 2. Android 工程 vs Xcode 工程 全景对照

先建立地图，再看细节：

| iOS | Android | 说明 |
|---|---|---|
| `.xcodeproj` / `project.pbxproj` | `settings.gradle.kts` + 各 `build.gradle.kts` | 最大差异：Android 工程结构是**纯文本脚本**描述的，可读、可 diff、可 code review，没有 pbxproj 合并冲突那种噩梦 |
| Bundle Identifier | `applicationId` | 应用在设备与商店的唯一身份 |
| `Info.plist` | `AndroidManifest.xml` | 都是"应用元数据"，但 Android 的四大组件（Activity 等）必须在此**显式注册**，iOS 没有这个概念 |
| Base SDK | `compileSdk` | 编译时能"看见"哪些 API |
| Deployment Target | `minSdk` | 最低支持的系统版本 |
| （无对应） | `targetSdk` | iOS 没有的概念：声明"我已适配到这个版本"，系统据此决定对你启用哪些新的兼容行为；国内商店对它有硬性下限要求（详见 §5） |
| `CFBundleVersion` | `versionCode` | 内部递增整数，商店用它判断新旧 |
| `CFBundleShortVersionString` | `versionName` | 用户可见版本号 |
| SPM `Package.swift` | `gradle/libs.versions.toml` | 依赖版本的单一真源（Version Catalog） |
| xcconfig | `gradle.properties` | 全局构建开关 |
| Xcode 内置构建系统 | Gradle wrapper（`gradlew`） | Android 连**构建工具本身**都被工程锁定版本——团队每个人、CI 用的都是同一个 Gradle，这是 iOS 没有的工程化优势 |
| 模拟器 + 真机运行 | 模拟器（AVD）+ 真机运行 | 体验类似；Android 真机调试免证书签名折腾，插上就能跑 |

**心智模型**：Xcode 是"IDE 即构建系统"，Android 是"IDE（Android Studio）只是 Gradle 的图形外壳"。所有构建行为都可以脱离 IDE 用命令行 `./gradlew` 复现——这也是 CI/CD 和多渠道打包（S9）的基础。

## 3. Gradle 全家桶逐文件讲解

工程根目录长这样（只列构建相关）：

```
WanReader/
├── settings.gradle.kts          ① 工程"户口本"
├── build.gradle.kts             ② 根构建脚本
├── gradle.properties            ③ 全局构建开关
├── gradle/
│   ├── libs.versions.toml       ④ 依赖版本目录（单一真源）
│   ├── gradle-daemon-jvm.properties  ⑦ 构建用 JVM 版本锁定
│   └── wrapper/                 ⑥ Gradle 自举器
│       ├── gradle-wrapper.jar
│       └── gradle-wrapper.properties
├── gradlew / gradlew.bat        ⑥ wrapper 启动脚本（Mac/Win）
└── app/
    └── build.gradle.kts         ⑤ app 模块构建脚本
```

### ① settings.gradle.kts —— 工程"户口本"

一句话定位：**声明这个工程有哪些模块、插件和依赖从哪里下载**。Gradle 启动后第一个读的就是它。

三个块逐一看（完整代码见工程文件，此处讲意图）：

- **`pluginManagement.plugins`**：插件版本的**单一真源**。Kotlin 的版本号全工程只在这里出现一次，模块里引用插件一律不写版本。为什么？版本写多处必然漂移，漂移必然在某天爆出诡异错误（见坑①）。
- **`pluginManagement.repositories`**：插件从哪下载。注意 `google { content { includeGroupByRegex(...) } }` 的写法——告诉 Gradle "只有 com.android/com.google/androidx 开头的组件才去 Google 仓库找"，避免每个依赖都跑三个仓库轮询，国内网络下提速明显。
- **`dependencyResolutionManagement`**：库依赖从哪下载。`RepositoriesMode.FAIL_ON_PROJECT_REPOS` 是企业规范——任何模块私自声明仓库直接构建失败，依赖来源全部集中管控（供应链安全 + 可审计）。
- **`rootProject.name` + `include(":app")`**：工程名与模块清单。S8 拆多模块时，就是往这里加 `include(":core:network")` 这样的行。

### ② 根 build.gradle.kts —— 只登记、不应用

一句话定位：**把插件登记到构建类路径，但不在根工程应用**（`apply false`），由各模块自行选用。

```kotlin
plugins {
    alias(libs.plugins.android.application) apply false
}
```

为什么这么绕？因为根工程本身不是一个 Android 模块，它只是"版本仲裁者"：保证所有子模块用的 AGP 是同一个版本。iOS 对照：≈ Podfile 顶部的全局声明区。

### ③ gradle.properties —— 全局构建开关

一句话定位：**对所有模块生效的构建参数**。本工程三行：

| 配置 | 作用 |
|---|---|
| `org.gradle.jvmargs=-Xmx2048m` | 构建进程内存上限；多模块后不够会报 OOM，届时上调 |
| `org.gradle.configuration-cache=true` | 配置缓存：脚本没变就跳过配置阶段，二次构建明显提速 |
| `kotlin.code.style=official` | Kotlin 官方代码风格 |

### ④ gradle/libs.versions.toml —— Version Catalog

一句话定位：**全工程依赖版本的单一真源**，iOS 对照 ≈ 把 Package.swift 里所有 `.package(url:from:)` 抽到一个集中清单。三段结构：

- `[versions]`：版本号变量池
- `[libraries]`：库坐标（group:name）+ 引用版本变量；在模块里写成 `implementation(libs.androidx.core.ktx)`（TOML 的 `-` 变成 `.`）
- `[plugins]`：插件 id + 版本；模块里写成 `alias(libs.plugins.kotlin.compose)`

注意 Compose 的玩法：`androidx-compose-bom` 是一个 **BOM**（Bill of Materials，清单账本），`implementation(platform(libs.androidx.compose.bom))` 之后，所有 Compose 库都不写版本号，由 BOM 统一定版。iOS 对照：≈ SPM 里一个 Package 统一带出一组版本兼容的子库。

**企业规范**：任何新依赖必须进 catalog，禁止在模块里写裸版本字符串 `"androidx.core:core-ktx:1.10.1"`。

### ⑤ app/build.gradle.kts —— 模块构建脚本

一句话定位：**app 模块自己的身份、SDK 面、构建变体和依赖**。逐块看：

- **`plugins`**：只有两个——`android.application`（这是个 App 而非库）和 `kotlin.compose`（Compose 编译器）。**没有 `kotlin.android`**，见坑①。
- **`namespace`**：R 类与 BuildConfig 的包名。AGP 8 起与 `applicationId` 解耦——前者是代码组织概念，后者是商店身份概念，S9 打渠道包时你会体会到解耦的好处（同一份代码打出不同 applicationId 的包）。
- **`compileSdk { version = release(36) { minorApiLevel = 1 } }`**：AGP 9 的新 DSL。Android 从 2025 年起 SDK 有了小版本（36.1），所以不再是简单的 `compileSdk = 36` 整数写法。
- **`defaultConfig`**：applicationId / minSdk / targetSdk / versionCode / versionName，对照表见 §2。
- **`buildTypes.release.optimization.enable = false`**：AGP 9 里 R8 混淆/优化的新开关（老项目里你会看到 `isMinifyEnabled` + `proguardFiles` 的写法）。S0 先关，S9 系统性开启并讲混淆规则。
- **`compileOptions`**：Java 字节码级别（Java 11）。Kotlin 编译出的字节码也要与它对齐。
- **`buildFeatures.compose = true`**：开启 Compose 编译支持。
- **`dependencies`**：注意三种配置的区别——`implementation`（编译+打包）、`platform(...)`（只定版不引库）、`debugImplementation`（只进 debug 包，如 ui-tooling 预览支持）。

### ⑥ gradle wrapper —— 构建工具的"自举器"

一句话定位：**保证任何人在任何机器上构建，用的都是同一个 Gradle 版本**。

`./gradlew` 脚本启动时读 `gradle-wrapper.properties` 的 `distributionUrl`（本工程锁定 9.4.1），本机没有就自动下载。所以新同事克隆代码后**不需要安装 Gradle**，`./gradlew assembleDebug` 直接能跑。

`gradle-wrapper.jar` 是自举逻辑本身，**必须提交进 git**——这正是本课坑④的案发现场，见 §5。

### ⑦ gradle-daemon-jvm.properties —— 构建 JVM 锁定

锁定构建守护进程用的 JVM 版本，配合 settings 里的 foojay 工具链插件：本机没有对应 JDK 会自动下载。这是治"JDK 版本不匹配"（坑③）的制度化方案。

## 4. AGP ↔ Kotlin ↔ compileSdk ↔ JDK：谁约束谁

Android 工程有四个"版本齿轮"，咬合关系如下：

```
AGP（Android Gradle Plugin）是中心齿轮：
  AGP 版本 → 要求最低 Gradle 版本（本工程：AGP 9.2.1 ← Gradle 9.4.1 ✓）
  AGP 版本 → 支持的 compileSdk 上限（AGP 9.x ← SDK 36 ✓）
  AGP 版本 → 要求最低 JDK 版本（AGP 9 需要 JDK 17+，AS 内置 JBR 已满足）
  Kotlin 版本 ↔ Compose 编译器插件版本（Kotlin 2.x 起强制同版本，本工程都是 2.3.20）
```

**本工程锁定值及理由**：AGP 9.2.1 / Kotlin 2.3.20 / Gradle 9.4.1 / compileSdk 36——这套组合已在本机的 demo_02/demo_03 上真机验证通过，S0 直接复用，不引入任何新变量。

**授人以渔——以后自己怎么判断版本兼容**：
1. AGP ↔ Gradle ↔ JDK 对照：官方文档 developer.android.com → "Android Gradle plugin release notes" 页首的兼容表
2. Kotlin ↔ Compose 编译器：Kotlin 2.0 起二者同版本发布，不再需要查表（老项目的 `composeOptions { kotlinCompilerExtensionVersion }` 是历史遗迹）
3. 升级顺序铁律：**先升 Gradle，再升 AGP，最后升 Kotlin**；一次只动一个齿轮，动完 Sync + 跑通再动下一个
4. Android Studio 菜单 Tools → AGP Upgrade Assistant 可以半自动升级并提示不兼容点

## 5. 坑与解决方案（本课 4 个，全部真实发生过）

### 坑① Kotlin 插件重复注入（demo_02 两次踩坑实录）

**报错原文**（两种形态）：
```
The request for this plugin could not be satisfied ... is already on the classpath with an unknown version
Cannot add extension with name 'kotlin', as there is an extension already registered with that name
```

**原因**：AGP 9.2.1 会**自动应用** `org.jetbrains.kotlin.android` 插件。你在模块 `plugins` 块里再声明一次（无论带不带版本号），就是重复注册。

**解法**：模块里**彻底删除** `id("org.jetbrains.kotlin.android")` 声明。Kotlin 版本只在 `settings.gradle.kts` 的 `pluginManagement.plugins` 里声明一次，供 `kotlin.plugin.compose` 等真正需要显式应用的插件引用。

**iOS 视角**：类似 CocoaPods 里同一个 Pod 被两个来源引入的 duplicate symbols——解法思路一致：只留一个权威来源。

### 坑② Gradle / 依赖下载慢或超时（国内网络）

**症状**：首次 Sync 卡在 "Downloading gradle-9.4.1-all.zip" 半小时不动，或依赖解析大量 `Read timed out`。

**解法 A（依赖镜像）**：在 `settings.gradle.kts` 的两个 `repositories` 块**首位**插入腾讯或阿里镜像：
```kotlin
maven { url = uri("https://mirrors.cloud.tencent.com/nexus/repository/maven-public/") }
// 或阿里：https://maven.aliyun.com/repository/public 与 .../google
```

**解法 B（wrapper 镜像）**：把 `gradle-wrapper.properties` 的 `distributionUrl` 换成腾讯镜像：
```properties
distributionUrl=https\://mirrors.cloud.tencent.com/gradle/gradle-9.4.1-all.zip
```

**提醒**：镜像有同步延迟（新版本发布后几小时到几天），团队项目建议把镜像放公共仓库**之前**而不是替换掉官方源；问题解决后是否保留镜像，团队要有统一约定，避免"我这能下你那不能"。

### 坑③ JDK 版本不匹配

**报错原文**（典型）：
```
Unsupported class file major version 65
Your build is currently configured to use incompatible Java 21.0.x and Gradle 8.x
```

**原因**：构建用的 JDK 和 Gradle/AGP 要求不匹配。常见于：终端里 `JAVA_HOME` 指向系统旧 JDK、或用了过新的 JDK 跑旧 Gradle。

**解法**（按优先级）：
1. Android Studio 里检查 Settings → Build, Execution, Deployment → Build Tools → Gradle → **Gradle JDK**，选内置的 JetBrains Runtime（JBR 17+）
2. 本工程已配置制度化兜底：`gradle-daemon-jvm.properties` 锁定构建 JVM + foojay 工具链插件自动下载缺失的 JDK
3. 命令行构建时确认 `./gradlew -version` 显示的 JVM 与预期一致

**iOS 视角**：≈ Xcode 版本与 Swift toolchain 不匹配的问题，但 Android 把"用哪个工具链"写进了工程文件，制度上更可控。

### 坑④ 根 .gitignore 吞掉 gradle-wrapper.jar（本课现场实录，2026-07-13）

**症状**：`git commit` 后发现 `gradle-wrapper.jar` 根本没进版本库——本仓库根目录的 `.gitignore` 有一条 Java 通用模板规则 `*.jar`，把它静默排除了。

**危害**：clone 这个仓库的人（包括 CI）执行 `./gradlew` 会直接失败——wrapper 脚本找不到自举 jar。这类问题**在你自己机器上永远不会暴露**（你本地有这个文件），是典型的"传染给别人才发现"的坑。

**解法**：在根 `.gitignore` 的 `*.jar` 规则后加例外，并补提交：
```gitignore
*.jar
!**/gradle/wrapper/gradle-wrapper.jar
```
```bash
git add -f WanReader/gradle/wrapper/gradle-wrapper.jar   # 或加例外规则后正常 add
```

**通用教训**：套用语言通用 .gitignore 模板后，用 `git status --ignored` 或 `git check-ignore -v <文件>` 检查是否误伤了必须提交的文件。

## 6. iOS 开发者最容易懵的 3 个点

**Q1：为什么有两个 build.gradle.kts？**
根目录那个管"全工程的插件版本仲裁"，`app/` 那个管"这个模块自己怎么构建"。iOS 只有一个 project 配置是因为 Xcode 工程默认单体；Android 从设计上就是多模块的（S8 你会新增好几个模块，每个都有自己的 build.gradle.kts，但根目录永远只有一个）。

**Q2：为什么改了配置要 Sync？Sync 到底做了什么？**
Gradle 脚本是**代码**不是静态配置，Android Studio 必须执行一遍它们才知道工程长什么样。Sync = 执行所有构建脚本 → 解析并下载依赖 → 把结果（模块结构、classpath、SDK 面）喂给 IDE 索引。iOS 对照：≈ SPM 的 "Resolve Package Versions" + Xcode 重建索引，只是 Android 把它显式化了。**改任何 `.gradle.kts` / `.toml` / `gradle.properties` 后都要 Sync**，IDE 顶部会出现提示条。

**Q3：local.properties 为什么不进 git？**
它记录**你这台机器**的 Android SDK 安装路径（`sdk.dir=/Users/you/Library/Android/sdk`），每个人机器不同，提交了反而害人。Android Studio 打开工程时会自动生成。iOS 对照：≈ DerivedData 路径这类本机偏好。已被 `.gitignore` 排除，Sync 后你会看到它出现但 `git status` 里没有它——这是正确状态。
